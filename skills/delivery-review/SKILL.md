# 交付协作工作流（Loop 模式）

> "你不知道远比你知道的要重要的得多。"——塔勒布

**执行入口：`/delivery-review` 命令。** 本文件是方法论与数据模型参考。命令内部已用 `.delivery-review/state.json` 状态机驱动循环，不依赖模型记忆轮次。

---

## 元认知原则

### 边界感知三层

| 层级 | 含义 | 必须输出 |
|------|------|---------|
| 已知 | 确定检查过，结论明确 | ✅ 确认 / ❌ 有问题 |
| 不确定 | 检查了但没把握 | ⚠️ + 原因 |
| 未检查 | 根本没覆盖到的维度 | 🔍 列出（最重要） |

**每个交付节点必须输出「未知清单」——列出 AI 无法确认的风险点。这个清单比检查清单更重要。**

### 审查结论三通道（第 4 层输出）

审查者输出的判断分三路走，不可混用：

| 通道 | 含义 | 去向 |
|------|------|------|
| risk | 确定（或高置信）的问题，带证据等级 | 触发修复 |
| 存疑清单 | 看了但拿不准的点（含经验猜测） | 不触发修复，人工验收判断 |
| 未知清单 | 没看 / 无法确认的维度 | 人工验收补查 |

## 角色与隔离

| 角色 | 执行者 | 权限 | 职责 |
|------|--------|------|------|
| 修复工程师 | `delivery-fixer` 子代理 | 读写代码 | 改代码、自检、处理 risk |
| 资深审查者 | `delivery-reviewer` 子代理 | **零命令权限（工具层禁止 Write/Edit/Bash）** | 按分级选择深度的独立审查（trivial 轻量模板 / standard·critical 两段式：第一性原理本质审查 → 症状审查）、报 risk（带证据等级 + 与目标的关系）、对抗自查、输出审查轨迹（供溯源）、打分、确认收敛 |
| 方案审查者 | `delivery-planner` 子代理（按需触发） | **零命令权限（工具层禁止 Write/Edit/Bash）** | 方案输出后、用户确认前，从产品视角审查方案（四项检查），结论只呈现用户，不进 git-notes |
| 编排者 | 主 Agent / `/delivery-review` | 读写 + spawn | 确认上下文、输出方案与目标、驱动 loop、裁决、代写审查者留言、人工验收、生成交付报告 |

> 审查者的「零命令」由 agent 定义的 `disallowedTools` 在工具层强制，不靠 prompt 请求。它看不到 diff 的问题由插件 **PostToolUse hook 自动生成审查材料**解决（见下），因此不需要任何命令权限。

## 通信机制与数据模型

### 存储（心智边界：机器工作台 vs 人的入口）

`.delivery-review/` 是机器工作台。**人只需要认识两个文件**，其余不用打开：

```
.delivery-review/
├── state.json            ← 人：瞄一眼状态（轮次/分数/退出原因）
├── review.log            ← 人：看审查历史（纯文本 append，tail/grep 友好）
└── work/                 ← 机器工作区，人不打开
    ├── material.md           hook 覆盖写：当前审查材料（给审查者子代理读）
    ├── material-rN.md        编排者复制：每轮材料快照（溯源用）
    ├── round-baseline.json   编排者每轮开头写：本轮起点（git tree 对象），hook 据此算增量
    ├── round-delta.json      hook 写：本轮文件清单/行数/是否与上轮全等，编排者只读不算
    └── hook.log              hook 异常日志（低频）
```

人的完整溯源入口是**交付报告**（`docs/delivery-review-*.md`）——报告已把对话实录、审查轨迹、快照索引组织成可读形式，不需要人翻工作目录。

- `state.json`：循环状态（机器判定），字段见下表
- `review.log`（**事件流式纯文本日志，无 markdown**）：每条事件一行，ISO 8601 时间戳打头 + 符号标记（▶ 开始 / ✔ 通过 / ✖ 有 risk），可排序可 grep；done 事件行后跟缩进载荷行（属同一时间点，不重复时间戳）。编排者在快照后写 begin、审查返回后写 done（两条时间戳相减即该轮审查耗时）：
  ```
  [2026-08-28T15:04:05+0800] ▶ ROUND 1 begin | tier=trivial | snapshot=work/material-r1.md
  [2026-08-28T15:05:12+0800] ✔ ROUND 1 done | score=8/10 | risk=0 (P0:0 P1:0 P2:0) | verdict=approve
      evidence: src/foo.ts:42 via Read; src/bar.ts:12 via Grep
      coverage: essence=ok bug=ok edge=ok regress=ok test=miss(no-runtime) refactor=ok deviate=ok
      tier-match: yes
      track: <审查者轨迹原文逐行原样>
  ---
  ```
- `work/material.md`：PostToolUse hook 在每次 Write/Edit/Bash 改动后覆盖刷新，头部元信息含生成时间 / 基线 HEAD / **风险分级 tier（hook 机械化判定）**，正文含改动清单 / 完整 diff（>800 行截断）/ 新建文件清单（untracked）。审查者 Read 该文件获取改动全貌，用 Read/Grep 核实代码
- `work/material-rN.md`：每轮审查前由编排者复制留存——材料本身会被覆盖，快照是中间状态的唯一留存（字节级溯源锚点）
- 路径落位：`.delivery-review/` 与交付报告 `docs/` 固定在仓库根目录（hook 与命令都按 `git rev-parse --show-toplevel` 定位），不在子目录创建
- 对话记录：`git notes --ref=delivery-review`（审查者留言由**编排者代写**——审查者零命令权限无法自行写入）
  ```json
  {
    "round": 0,
    "last_score": 0,
    "exit_reason": "",
    "max_rounds": 3,
    "open_risk_ids": [],
    "legacy_risk_ids": [],
    "defer_risk_ids": [],
    "started_at": "2026-08-28T15:04:05"
  }
  ```

| 字段 | 类型 | 用途 |
|------|------|------|
| `round` | int | 当前轮次 |
| `last_score` | int | 上一轮质量分（退出判定用） |
| `exit_reason` | string | 退出原因（空 = 继续） |
| `max_rounds` | int | 最大轮次上限 |
| `open_risk_ids` | int[] | 未解决的阻塞项：**本次引入 P0/P1 + 既有 P0**（为空 = 满足退出条件之一；P2 不进池） |
| `legacy_risk_ids` | int[] | 已登记的**既有问题**（老代码本来就有，不含既有 P0），不参与退出判定，验收时逐条呈现 |
| `defer_risk_ids` | int[] | 延后的 **P2**（不阻塞退出，但必须持久化，验收时从该字段读取，不靠回忆） |
| `started_at` | string | 本次运行开始时间（交付报告计算总耗时；每轮时间戳在 review.log） |

### 留言格式

```
<ID>|from|<type>|<reply_to>|<正文>
```

| 字段 | 说明 |
|------|------|
| ID | 递增整数，当前最大 ID + 1（审查者留言由编排者代写，ID 由编排者告知审查者后编号） |
| from | claude / reviewer / system |
| type | context / review / risk / done / score / approve / dispute / confirm / withdraw |
| reply_to | 回复的留言 ID，无则 0 |
| 正文 | 不含竖线 `|`（需转义为 `\|`） |

### type 枚举

| type | 谁发 | 含义 |
|------|------|------|
| `context` | 编排者 | 目标 + 背景 + 方案 |
| `review` | 修复方 | 改动说明 + 意图声明 + 验证证据 + 自检 + 未知清单 |
| `risk` | 审查方 | 问题描述 + 分级 + 证据等级 + 证据出处 + 归属 + 与目标的关系（必填） |
| `done` | 修复方 | 对某条 risk 的处理结果 |
| `score` | 审查方 | 本轮质量评分 + 收敛判断 |
| `approve` | 审查方 | 所有 risk 已解决，建议人工验收 |
| `dispute` | 修复方 | 对某条 risk 的反驳（附理由） |
| `confirm` | 审查方 | 收到 dispute 后自我核查结果（仍坚持） |
| `withdraw` | 审查方 | 撤回原 risk（误判） |

### 两段式审查（第一性原理，delivery-reviewer 强制）

1. **本质审查（先做）**：目标还原 → 核心断言提取 → 断言验证（带证据等级）→ 本质差距（目标 vs 改动 gap）
2. **症状审查**：bug / 边界 / 回归 / 测试 / 超范围重构 / 偏离目标（原六项）
3. **对抗自查（每轮必做）**：对每条正式 risk 三问——反证（修了目标真会达成吗）/ 根因（是因还是果）/ 目标本身（是否可验证）；P0/P1 额外给「fixer 可能的反驳 + 为何仍坚持」
4. **「与目标的关系」填不出** = 非本质问题，降 P2 或进存疑清单

### 证据等级（risk 必带字段）

| 等级 | 含义 | 处理规则 |
|------|------|---------|
| 已验证 | **有实际运行输出为凭** | 正式 risk；报此级必须引用 fixer/编排者提供的验证证据（命令 + 输出），引用不出则降级 |
| 可复现 | 给出了复现步骤（未实际运行） | 正式 risk |
| 代码推断 | 读代码推断的（无运行依据） | 正式 risk，但**不允许报 P0** |
| 经验猜测 | 无具体依据的怀疑 | **不算 risk**，只能进存疑清单 |

> P0（最严重）必须带"已验证 / 可复现"证据；状态机统计 risk 数与 P0/P1 判定时，**排除经验猜测级**（它不进入 risk 流）。
>
> **审查者零命令权限的结构性限制**：审查者被禁 Bash，自己跑不了任何东西，所以「已验证」的出处只能是修复方或编排者提供的运行证据。**没有证据支撑的「已验证」一律降级为「可复现 / 代码推断」**——这条不是形式要求，是防止审查结论虚高的唯一约束。

### 验证证据（1.7.0 起强制）

- **fixer 的 review / done 留言必须含【验证证据】**：实际执行的命令 + 输出关键行；跑不了写「未运行 + 原因」
- **编排者代跑**：Step 1 方案里用户确认的「改完怎么验证」若能落成命令，编排者跑一次，结果写入 `review.log` 的 `verify:` 行并贴进 reviewer prompt；跑不成命令的标注「未代跑 + 原因」，不自行发明命令
- **审查者零命令权限**，判「已验证」只能引用上述两段证据之一，引用不出即降级
- **验证失败不是日志噪音**：必须作为下一轮 fixer 的必修输入，并在 Round 结果与验收中显式呈现

### 同类一次修完（1.7.0 起）

fixer 处理每条 risk 时扫一遍同类位置（同根因 / 同模式），留言写「同类排查：扫描范围 / 另有 N 处 / 已修或未修原因」。超出本次目标的同类问题只报告不动手，交人工决定是否扩大范围。

### 漏检复盘（1.7.0 起，仅验收不通过时）

交付报告新增该段：当时审查材料缺了什么 / 哪条规则没覆盖 / 建议沉淀到 CLAUDE.md、SKILL.md、agent 定义还是 hook，为下次同类问题留抓手。

### 风险归属（risk 必带字段，本次改动新增）

| 归属 | 判定依据 | 处理 |
|------|---------|------|
| 本次引入 | 位置落在相对基线 HEAD 的累计 diff 改动行内 | 计入 `open_risk_ids`，阻塞退出（P0/P1） |
| 既有问题 | **位置不在相对基线 HEAD 的累计 diff 改动行内**（必须给出依据） | 计入 `legacy_risk_ids`，不阻塞退出，验收时逐条呈现；**既有 P0 例外，进 `open_risk_ids` 阻塞** |

> 老问题不因「不是这次改的」就消失，但也不该占用修复轮次、抬高改动计数——分离登记是为了让两者都不被糊弄。既有 P0 例外：同样必须修，因此进 `open_risk_ids` 一并阻塞退出。
>
> **归属依据的基准是「相对基线 HEAD 的累计 diff」**（材料给的是整个 loop 的改动，不是单轮增量）：本 loop 改过这块 → 本次引入；从没碰过 → 既有问题。

### 风险分级

| 级别 | 含义 | 处理要求 |
|------|------|---------|
| P0-阻塞 | 安全漏洞、数据丢失、功能不可用 | 必须修复才能退出 loop（需已验证/可复现证据） |
| P1-重要 | 逻辑错误、性能退化、边界缺失 | 必须修复或说明不修复理由 |
| P2-建议 | 代码风格、命名、可维护性 | 可 defer，人工验收时酌情处理 |

## 风险分级路由（审查深度与风险对价）

固定开销（多次确认 / 子代理冷启动 / 两段式全套 / 独立报告）对大改动是保险费，对小改动是纯税——**1 分钟的改动不该走 20 分钟的仪式**。分级让深度随风险伸缩：

| tier | 判定（hook 机械化，LLM 不参与） | 流程 |
|------|------|------|
| trivial | 文件 ≤2 且 diff ≤30 行且不触碰关键路径 | 一次确认 / 主会话直改不 spawn fixer / reviewer 轻量模板一轮定音 / 精简验收 / 不生成独立报告 |
| standard | 其余 | 完整流程 |
| critical | 触碰关键路径（hooks/、CI、auth、migration、security 等）或文件 >5 或 diff >300 行 | 完整流程；若最终以 max_rounds 兜底退出，交付报告【流程档位】必须显著标注「critical 级未收敛退出」，人工验收从严 |

**两级判定，不一致从严**：
- 入口（Step 1）：编排者给预估档位，用户可选快车道——这是路由建议，靠用户在环把关
- 出口（Step 3.0）：hook 按实际改动机械判定 tier 写进材料头部——预估 trivial 实际 standard/critical → 自动升级完整流程，轮次重计。**分级规则在 hook 代码里，不依赖提示词自觉，永不在上下文压缩中失忆**

**可观测性不分档**：快车道同样落盘审查轨迹（轻量版）与材料快照——深度可以降，留痕和边界声明不可省，否则快车道就是黑箱快速通道。

## 可观测性与溯源（隔离的对价：过程必须结构化带出来）

子代理是销毁式上下文——审查者看了什么、凭什么判 risk，随子代理结束蒸发，编排者只拿到结论。隔离买来无污染视角，**可观测性必须作为对价显式补回**，否则人工复核断链。四个留存层：

| 层 | 载体 | 回答的问题 |
|----|------|-----------|
| 对话实录 | git-notes（交付报告中原样渲染） | 谁说了什么：risk 怎么提出、fixer 怎么回应、dispute 怎么收场 |
| 审查轨迹 | review.log（审查者每轮必输出，编排者原样落盘） | 凭什么这么说：实际 Read/Grep 过的 文件:行号、维度覆盖 ✅/⚠️/🔍、实际风险与分级是否相符 |
| 材料快照 | work/material-rN.md（审查前编排者复制） | 当时看到的是什么：材料每轮被 hook 覆盖，中间状态没有 commit 可回放，不快照即永久丢失 |
| git 锚点 | 基线 HEAD → 终态 diff | 终态复核：交付完随时可 diff 对照 |

机制约束：审查者保持零写权限，日志由编排者代写（与 git-notes 代写同构）——**留痕需求不松动物理边界**。审查轨迹里的核实位置必须真实（它就是「代码推断」级证据的出处），没有轨迹的审查结论无效。

## Loop 退出条件（由 state.json 状态机判定，优先级从高到低）

1. **dispute 未解** → 强制退出，移交人工裁决
2. **stalled**：本轮工作区与上轮全等（`round-delta.same_as_prev`）但 `open_risk_ids` 非空或分数不达标 → **没进展且活没干完**，强制人工裁决
3. **no_progress**：本轮工作区与上轮全等且 `open_risk_ids` 为空、分数 ≥7 → 正常收口，走验收（quality_gate 的真子集，行为无差异，仅报表区分）
4. **quality_gate**：`open_risk_ids` 为空（无未解决的本次引入 P0/P1 与既有 P0）且 `质量分 >= 7` → 正常退出（首轮满足即当轮退出）
5. **max_rounds**：达到 `max_rounds`（默认 3）→ 兜底退出

> **震荡判据已重定义（1.8.0）**：删除 `file_mod_counts >= 3`（阈值与 `max_rounds` 相等，正常 loop 跑满必然误判；且按累计 diff 计数，「没改也 +1」）。震荡的本义是「原地打转」。
>
> **覆盖面（勿夸大）**：`stalled` / `no_progress` 只抓「工作区零改动」这一种卡死；**「改了但风险不减少」的反复无效改动没有专门判据，仍由 `max_rounds` 兜底**。
>
> **两条判据在 `max_rounds ≤ 3` 下结构上不可达，已移除**：`risk reopen ≥ 2 次`（最快第 4 轮才成立）、`A→B→A 回摆`（最早第 3 轮，与 `max_rounds` 同时到点，只换标签不产生行为差异）。若未来调大 `max_rounds`，需重新评估是否恢复——**恢复前先按新的 `max_rounds` 走一遍路径验算可达性**。
>
> **本轮增量来自 `work/round-delta.json`，不由 LLM 数文件**：该文件由 hook 生成（文件清单 / 文件数 / 行数 / `same_as_prev`），编排者只读不算。
>
> **不再设「连续两轮收敛」一道门**：实测四个真实运行项目（deepseek-harness-plugin / desktop-pet / pi-web / Folder-Chinese），收敛均在首轮或次轮达成，唯一走到 max_rounds 的是一轮只读扫描（P1 未修，属规则正常拦截）。「重复上报被算成新增导致收敛不了」是臆想痛点，故取消 `consecutive_clean` 计数与 risk 签名去重，退出只看「本次引入 P0/P1 是否清零 + 分数」。
>
> **P2 不阻塞退出但要登记**：P2 只进 `defer_risk_ids`，一轮全是 P2 时分数达标即退出，不空转；验收时从该字段读，不靠回忆。
>
> **既有问题不阻塞退出，但必须显式呈现**：登记进 `legacy_risk_ids`，验收时逐条列出由用户决定是否另开任务。P0 例外——既有 P0 同样必须修，因此进 `open_risk_ids` 阻塞退出。归属判定必须附证据（该位置不在相对基线 HEAD 的累计 diff 改动行内），否则按「本次引入」从严处理。
>
> **池内条目只能经三个明确出口离开**：① 审查者在「上轮未解决 risk 复查」段落写「✅已修复 + 证据」（证据须锚定到相对基线 diff 的改动行）② 审查者 withdraw 或在复查段判「误报」（`review.log` 记 `withdrawn:` 行）③ **本轮任一 risk（含 P2）**的 `reply_to` 指向旧 ID → 链归并为最新 ID，旧 ID 标 superseded 出池（记 `superseded:` 行；降级续报 P1→P2 同样走此出口，新 P2 进 `defer_risk_ids`）。「本轮没再提」不构成出池理由。
>
> **为什么三个出口都要有**：只留「已修复」一个出口，审查者一旦撤回误报，那条 ID 就永远离不开池子——收敛判定会从「可能被静默清空」变成「可能永久卡住」，同一部位反向失败。续报不归并则同一问题占两个 ID，重复计数问题换形态复现。
>
> **编排者两条抽检**：① ✅ 证据（≤2 条全查，>2 条至少查一半；不合格退回池记 `verify-reject:`）② 既有问题归属（每轮至少查 1 条，确认确实不在累计 diff 内；不合格改判本次引入重新入池记 `misfiled:`）。审查者「省事全标 ✅」或「把问题标成既有来逃避」的收益都大于成本，光靠自觉约束不住。
>
> **状态机执行纪律**：编排者每轮必须输出完整 state update block，`open_risk_ids` / `legacy_risk_ids` / `defer_risk_ids` 全量写回，不依赖 LLM 记忆或心算。

## Dispute 机制

```
审查方发 risk
  ↓
修复方不同意 → dispute（反驳理由 + 证据）
  ↓
审查方自我核查
  ├─ 仍认为有问题 → confirm → 退出 loop，人工裁决
  └─ 发现误判   → withdraw → 继续 loop
```

> 经验猜测级问题不算 risk，不存在 dispute 流程；存疑清单在人工验收时统一判断。

## 用户介入（任意时刻）

- **检查点**：每轮子代理返回后、状态机更新前，编排者检查用户是否有新消息，有则先输出进度摘要再对齐
- **打断**：用户 Esc 终止子代理，编排者恢复后优先处理用户消息
- **目标变更** = 与 Step 2 相同的完整重置（state.json 归零 + 删旧材料 + 新 context 留言）；**仅澄清** = 轮次延续
- 响应最迟不迟于当前子代理返回

> fixer 被打断可能留下半成品：重新对齐后以**当前工作区状态**为起点，不基于旧目标续写。

## 人工验收（最后一道防线：裁决权不可由 AI 代理）

红线拆两层：
- **裁决权**（通过/不通过）不可由 AI 代理——必须用户行使
- **验证执行**（跑测试 / 查日志 / 收集证据）可由用户声明交由 AI 代验，输出标注证据等级（已验证 / 代码推断），最终裁决仍由用户拍板

| 范围 | 内容 | 必须/可选 |
|------|------|----------|
| 改动点 | 修复方修改过的代码对应功能 | 必须 |
| 未解决项 | loop 中未解决的 risk | 必须 |
| 撤回 / 归并记录 | 从 review.log 的 `withdrawn:` / `superseded:` 行读取，说明消失的条目去了哪 | 必须 |
| 审查方存疑清单 | 拿不准的点（含经验猜测） | 必须 |
| 双方未知清单 | 修复方与审查方都无法确认的风险 | 必须 |
| 卡死点 | 本轮零改动但未收敛（`exit_reason=stalled`） | 必须 |
| 回归测试 | 原有功能是否被破坏 | 可选 |
| 体验检查 | 操作顺畅度、提示清晰度 | 可选 |

## 交付报告

Loop 结束后（无论验收结果），编排者把**本轮**留言整理为交付报告写入运行项目 `docs/delivery-review-<日期>-<HHmm>.md`：目标 / 方案（含用户选择）/ 流程档位 / 轮次摘要 / 已解决与未解决 risk / 存疑清单 / 未知清单 / **对话实录（本轮全部留言原样渲染）** / **审查轨迹汇总（引用 review.log）** / **材料快照索引** / 运行耗时 / 验收结论（未通过则标注原因与待办）/ AI 代验结果（如有）。报告是否提交 git 由用户决定。

> trivial 快车道不生成独立报告文件——review.log 条目 + git-notes 即交付记录，精简验收呈现时附两者路径。

## 附：塔勒布元认知速查

1. **我知道什么？** —— 确定检查过的
2. **我不确定什么？** —— 检查了但没把握的
3. **我不知道什么？** —— 根本没想到要检查的（最重要）
4. **如果我错了，后果是什么？** —— 下行风险不对称性
5. **这个改动重复一万次，会在某一次崩溃吗？** —— 遍历性检验

> 火鸡在被杀前的每一天都通过了「自检清单」。未知清单才是真正的防线。
